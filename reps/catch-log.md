# Catch-Log — Sprint 1 (recognition only)

An instantiation of `parents/behavior-rewiring/protocols/single-target-sprint.md` for this
grove's cue. The protocol is the parent's; the cue, the log and every line in it are ours.

## The target

> **When** someone gives me advice I did not ask for, or pushes past something I said,
> **I** notice it and write one line about it afterwards.

**Recognition only.** Change nothing in the moment. Do not try to respond better, hold
frame, or say anything you would not otherwise have said. The sole job this sprint is
detecting that it happened — the parent sanctions this as a legitimate first sprint
(`protocols/single-target-sprint.md` §1, last bullet) and this grove's `principles.md`
names recognition as rung 1, the thing that breaks first for this profile.

**Why this cue.** It fires on a predictable schedule in at least two contexts already
observed (unsolicited advice from a close relation, and dating-frame tests), which makes
it the shared cue the parent's §3 asks you to name out loud rather than two separate
targets.

**Proposed, not agreed.** The cue above is a suggestion from the review that created this
file; replace it if a different one fires more often or is easier to detect. Do not run
two.

- **Window:** 30 days from first entry.
- **One active target.** Everything else goes on the queue below, not into this log.
- **Noticing it an hour later counts as a win** and must be logged as one. A log that
  only rewards clean catches records nothing for two weeks and then dies.
- **Do not add columns.** The log competes with the thing it measures.

## Known problem, unresolved: capture friction

Flagged by the practitioner before the first entry, and it is the right objection. This
log assumes you will open a file in a git repo after the conversation has ended. In
normal life that is a lot of friction, and friction is how logs die — which matters more
than usual here, because the parent's `sources.md` §8 makes the log an active ingredient
rather than bookkeeping. A log that doesn't get filled isn't a weaker version of this
protocol, it is the absence of it.

Not solved yet. Candidate directions when we take it up: phone-side capture that syncs
here later, a single daily prompt instead of per-incident capture, voice, or dropping to
a tally mark with the one-line reconstruction done weekly. The parent's constraint on all
of them is §4's rule — don't add fields — not the medium, so the medium is ours to change.
